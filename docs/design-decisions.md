# Overview

개인 블로그의 설계 결정과 그 이유, 수용한 비용, 알려진 제약을 관리한다. 구현을 변경할 때는 기존 결정을 결함으로 오인하지 않도록 판단 근거를 확인하고, 결정이 달라지면 해당 항목을 갱신한다.

# Checkpoints

## 설계 전제와 정책

- **SSR과 SSG의 역할:** Express는 개발과 요청 시점 렌더링을 담당하며, 실제 배포에는 필요하지 않습니다. 렌더러를 공유해도 실행 시점과 데이터 제공 방식이 달라 두 환경의 동작이 완전히 같지는 않습니다. 태그 선택도 SSR은 요청 쿼리를 초기 데이터에 반영하고, SSG는 선택 없는 HTML로 hydration한 뒤 URL의 선택을 적용합니다. [SSR](SSR.md) · [SSG](SSG.md)
- **완전한 배포 빌드:** 배포는 `npm run build`로 번들·HTML·JSON·버전 맵을 함께 갱신합니다. 일부 단계만 실행한 산출물은 최신 배포를 구성하지 못할 수 있으며, 정적 서버 실행 중 소스 변경도 재빌드해야 반영됩니다. [빌드 명령](../package.json) · [배포 워크플로](../.github/workflows/deploy.yml)
- **배포 단위의 최신성:** 캐시 판단은 HTML에 포함된 빌드 시점의 버전 맵을 기준으로 합니다. 새 맵은 HTML을 다시 받을 때 반영되며 SPA 이동만으로 갱신되지 않습니다. 글·JSON·에셋을 함께 생성하는 정적 블로그를 전제로 하므로, 실시간 데이터에는 별도의 최신성 정책이 필요합니다. [캐시 설계](ETag-Map.md)
- **잘못된 콘텐츠의 처리:** 중복 글 ID와 잘못된 메타데이터는 자동 보정하거나 덮어쓰지 않고 빌드를 실패시킵니다. 필수 필드는 문자열이고 날짜는 실제로 존재하는 `YYYY-MM-DD`여야 합니다. 빈 제목은 허용하되 화면과 문서 제목에서 ID로 대체합니다. 생성 대상 밖의 경로와 존재하지 않는 글·태그·목록 페이지는 SSR에서도 404로 처리하며, 콘텐츠 자체의 검증 실패가 404로 숨겨지지 않도록 구분합니다. [콘텐츠 검증](../server/utils.ts) · [HTTP 계약 테스트](../server/server.test.ts)
- **기존 글 주소의 보존:** 파일명과 버전 맵 키는 원문을 유지하고 URL 경계에서 인코딩합니다. 기존 pathname 표기는 Giscus의 댓글 연결에도 사용되므로 불필요하게 바꾸지 않습니다. [공유 URL 함수](../shared/common.ts) · [Giscus pathname 매핑](https://github.com/giscus/giscus/blob/main/client.ts) · [URL 회귀 테스트](../tests/e2e/content-urls.spec.ts)
- **자동 검사와 배포:** `main` push와 `main` 대상 PR에서 앱·서버 유닛·브라우저 테스트 코드의 타입 검사와 유닛 테스트를 실행하며 실패 시 빌드·배포를 중단합니다. PR은 검사만 하고, `content/**`만 바뀐 PR은 워크플로를 실행하지 않습니다. 콘텐츠만 바뀐 push는 검사를 생략해 빌드·배포하고, 수동 실행은 항상 검사합니다. E2E·캐시·성능 테스트는 로컬 Docker에서 필요한 범위를 실행합니다. [자동 검사 설정](../.github/workflows/deploy.yml) · [테스트 실행](testing.md)

## 수용한 트레이드오프

- **빌드 비용과 HTML 크기:** 정적 페이지마다 전체 글의 태그를 다시 집계하고 전체 버전 맵을 각 HTML에 삽입합니다. 글이 늘면 빌드 비용과 HTML 크기가 증가하지만 구현·유지보수의 단순성을 위해 수용합니다. [초기 데이터 생성](../server/utils.ts) · [맵 주입](../scripts/inject-etag-map.js)
- **SSR 목록 캐시:** 실행 중 콘텐츠를 바꿔도 이미 읽은 최근 글·태그별 목록은 갱신되지 않을 수 있습니다. 상세 조회와 HTML의 태그 집계에는 변경이 반영되어 목록 API와 차이가 생길 수 있지만, 캐시 무효화를 추가하는 대신 서버를 재시작합니다. [Express 서버](../server/server.ts) · [콘텐츠 변경 시 재시작](../compose.dev.yaml)
- **초기 화면 이후의 JSON 요청:** 초기 HTML은 전체 태그 집계와 글 상세 데이터를 포함하고, 홈·검색·태그별 목록은 브라우저에서 JSON을 요청합니다. 최근 글은 페이지별로 받으며 태그별 목록은 전체를 받아 브라우저에서 페이지를 나눕니다. 정적 API를 단순하게 유지하기 위해 추가 요청과 대기를 수용합니다. [공유 데이터 계약](../shared/common.ts) · [정적 API 생성](../server/gen-api-resource.ts)
- **검색 준비 대기:** 검색 누락을 막기 위해 전체 목록 JSON이 준비될 때까지 입력을 비활성화합니다. 일부 요청이 실패하거나 시간 초과가 발생하면 불완전한 자료로 검색을 활성화하지 않습니다. [검색 구현](../src/pages/Search.tsx) · [요청 실패 테스트](../tests/e2e/request-failures.spec.ts)
- **에셋 변경 감지 정확도:** 버전 맵은 HTTP `ETag` 헤더와 별개입니다. JSON·HTML·MD는 MD5, 글 HTML은 원본 Markdown 해시를 사용하지만 나머지 에셋은 파일 읽기·해시 계산 비용을 줄이기 위해 `파일명-크기`를 사용합니다. 같은 이름·크기의 내용 변경을 구분하지 못하는 것은 수용한 제약이며 미해결 결함으로 취급하지 않습니다. [버전 맵 생성](../scripts/inject-etag-map.js)
- **hydration 전 동기화 대기:** 버전 맵이 있는 프로덕션 문서는 초기 effect가 이전 맵으로 JSON을 요청하지 않도록 SW의 문서별 맵 저장 ACK를 기다립니다. 초기 HTML은 먼저 표시되지만 React 이벤트와 effect는 이 대기 이후 시작합니다. 동기화 시작부터 controller 확보와 ACK 수신까지 최대 2초이며, 최초 설치의 다운로드·설치 시간도 포함됩니다. 개발 환경은 대기를 생략합니다. [클라이언트 진입점](../src/entry-client.tsx) · [동기화 구현](../src/lib/serviceWorker.ts)
- **배포 경계의 리소스 혼용:** 문서별 맵은 탭 사이의 덮어쓰기를 막지만 응답 캐시는 URL별로 공유합니다. 이전 문서의 캐시 미스에 새 배포의 응답이 오면 이전 문서 맵의 버전으로 저장될 수 있습니다. 이전 문서와 새 리소스가 함께 사용되는 것을 허용하며, 이전 배포의 응답 본문 보존을 보장하지 않습니다. [Service Worker](../public/sw.js)

## 지원 범위와 알려진 제약

- **대표 이미지 미지원:** `image`와 관련 코드는 향후 확장을 위해 남겨둔 것입니다. 직접 SSR한 메타데이터에는 해당 이미지가 들어갈 수 있지만 SPA 탐색에서는 기본 이미지로 바뀌며, 이 불일치를 수정하지 않는 제약으로 수용합니다. 본문 이미지는 사용할 수 있습니다. [SSR 메타 생성](../src/entry-server.tsx) · [SPA 메타 갱신](../src/pages/Post.tsx)
- **HTTP 스트리밍 미지원:** 공통 렌더러는 `renderToPipeableStream` 결과를 문자열로 모아 반환하며 Express 응답에 직접 스트리밍하지 않습니다. [공통 렌더러](../src/entry-server.tsx)
- **브라우저 렌더링 경계:** Markdown·Giscus는 지연 로딩하고 Mermaid SVG는 브라우저에서 생성합니다. 테마는 초기 HTML 스크립트에서 복원하며 테마 버튼은 마운트 후 표시해 초기 렌더의 일치를 유지합니다. [글 화면](../src/pages/Post.tsx) · [Mermaid](../src/components/Mermaid.tsx) · [테마 버튼](../src/components/Nav.tsx)
- **콘텐츠 이름의 이식성:** 글 ID·태그는 `< > : " / \ | ? *`, 제어 문자, Windows 예약 이름(`CON`, `NUL.txt` 등), 끝 공백·마침표를 허용하지 않습니다. 생성 파일명은 확장자 포함 UTF-8 255바이트 이내여야 하며, 글 ID만 대소문자와 무관하게 `.html`로 끝날 수 없습니다. 정적 HTML 주소 충돌을 막고 Windows·Linux에서 같은 산출물을 만들기 위한 제한이며, 전체 경로 길이와 파일시스템별 유니코드 정규화까지 보장하지는 않습니다. [이름 검증](../server/utils.ts) · [이름 회귀 테스트](../server/utils.test.ts)
- **태그 구분자:** `keywords`의 쉼표는 태그 구분자이므로 태그 이름 안의 쉼표는 지원하지 않습니다. 주변 공백은 제거하고 빈 문자열은 태그 없는 글로 허용합니다. [콘텐츠 검증](../server/utils.ts)
- **요청 대기 상한:** 글 상세·홈·태그 목록과 검색의 각 목록 요청은 응답과 JSON 처리에 10초 상한을 적용합니다. 글 상세·홈·태그 목록은 같은 조건으로 재시도하고 검색은 새로고침으로 복구합니다. 화면 이동에 따른 취소는 오류 안내 대상이 아니며, 이전 요청의 응답·실패·타이머가 현재 상태를 바꿀 수 없습니다. [요청 실패 테스트](../tests/e2e/request-failures.spec.ts)
- **캐시 적중의 조건:** 최초 방문에 에셋을 미리 캐시하지 않습니다. SW가 제어하는 요청으로 응답과 버전이 저장된 뒤, 요청 문서의 맵과 버전이 일치할 때만 네트워크 왕복 없는 적중이 가능합니다. HTML은 네트워크를 우선하며, 맵이나 버전이 없는 요청도 버전 일치 판정을 생략합니다. hydration 이전 에셋 요청의 순서는 보장하지 않습니다. [캐시 요청 처리](../public/sw.js)
- **동기화 실패와 오프라인:** SW 미지원·제어 SW 없는 등록 실패는 일반 요청을 사용합니다. 제어 SW의 맵 저장 실패·미지원 ACK·시간 초과 시에는 hydration을 진행하고 동일 출처 GET API를 캐시 우회·HTTP 재검증으로 요청하므로, 해당 API에는 오프라인 캐시 fallback이 없습니다. controller 전환에도 같은 대기 상한을 적용하며 저장 확인 전에는 우회하고 시간 초과 뒤 늦은 ACK는 무시합니다. 우회 상태는 다음 controller의 동기화나 문서 재방문으로 복구합니다. [동기화 구현](../src/lib/serviceWorker.ts) · [업그레이드 테스트](../tests/cache/upgrade.spec.ts)
- **정상 캐시 경로의 실패 처리:** HTML 요청과 에셋·API 캐시 미스는 HTTP 캐시를 재검증합니다. 2xx만 저장하고 HTTP 오류는 그대로 반환합니다. 네트워크 요청 자체가 실패하면 기존 캐시를 사용하므로 오프라인 응답은 오래될 수 있으며, 캐시가 없으면 실패합니다. 캐시 저장소를 열거나 조회하지 못해도 정상 네트워크 응답은 제공해야 합니다. 로컬 HTTP TTL은 SW Cache Storage의 만료 시간이 아닙니다. [Service Worker](../public/sw.js) · [저장소 장애 테스트](../tests/cache/bootstrap.spec.ts)

# Tests

## 검증 범위와 해석

- **환경별 확인:** Express SSR 실행은 SSG 배포 검증을 대신하지 않습니다. 로컬 정적 서버도 GitHub Pages CDN까지 재현하지 않으므로, 확장자 없는 직접 접근과 새로고침은 실제 배포에서도 확인해야 합니다. SPA 내부 이동 성공만으로 정적 HTML의 존재를 판단하지 않습니다. [SSG 문서](SSG.md)
- **브라우저 테스트의 범위:** 테스트 전용 콘텐츠를 사용한 로컬 Nginx·Chromium 검증입니다. 초기 에셋 전체의 최신성과 GitHub Pages CDN 동작은 별도 확인 대상이며, 통제한 경합의 재현으로 운영 장애 빈도를 추정하지 않습니다. [테스트 문서](testing.md)
- **캐시 테스트 실행 비용:** 배포 링크를 공유하므로 브라우저 테스트는 worker 하나로 실행합니다. 병렬화하려면 서버·볼륨을 분리해야 하며, 재시도는 첫 접속 실패를 가릴 수 있어 끕니다. [Playwright 설정](../tests/playwright.config.ts)
- **성능 지표의 한계:** `app:cache-sync`는 초기 SW 준비·ACK 대기 시간과 결과, `app:hydrate-start`는 hydration 호출 시점입니다. 이후 controller 전환이나 hydration 전체 완료·입력 지연을 뜻하지 않습니다. 외부 폰트·CPU·스토리지·네트워크의 영향을 받는 로컬 소수 표본으로 실서비스 성능 상한이나 서로 다른 캐시 상태 간 개선율을 단정하지 않습니다. [측정 방법](testing.md#성능-측정)

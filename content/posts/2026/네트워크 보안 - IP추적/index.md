## 메일을 통한 IP주소 추적
이메일의 헤더를 분석하면 메일이 거쳐 온 서버의 IP 주소와 전송 경로를 확인할 수 있다.
* Received 헤더: 메일 서버가 메일을 수신할 때 추가하는 정보로, 이전 서버의 IP 주소와 수신 시간 등을 기록한다.
* 분석 순서: 새로운 Received 정보는 헤더의 위쪽에 추가되므로, 일반적으로 아래쪽부터 위쪽으로 분석한다.
* 최초 수신 정보: 최초로 메일을 수신한 서버의 정보가 발송 경로를 파악하는 데 중요하다. 다만 해당 정보의 신뢰성을 확인해야 한다.

최초 수신 정보가 사설 IP 주소라면 내부 네트워크를 거쳤을 가능성이 있으므로, 이후의 신뢰할 수 있는 공인 IP 주소를 확인한다.

> 메일 헤더는 발신자의 실제 IP 주소가 아닌 메일 서비스 제공업체의 서버 IP만 기록될 수 있으며, 일부 헤더 정보는 위조될 수 있다.

## P2P 서비스를 통한 IP 주소 추적
Peer-to-Peer 는 클라이언트 간에 직접 데이터를 주고받을 수 있는 통신 방식이다.

* 서버 경유: 연결 설정이나 상대방 탐색 등에 서버를 이용할 수 있다.
* 직접 연결: 클라이언트 간 직접 통신이 이루어진다면 상대방의 연결 IP 주소를 확인할 수 있다.
* 분석 도구: `netstat`, `Wireshark` 등을 이용하여 네트워크 연결 및 패킷 정보를 분석한다.

> 모든 P2P 통신이 직접 연결되는건 아니고, 중계 서버를 이용한다면 상대방의 IP 대신 중계 서버의 IP가 확인될 수 있다.


## 웹 게시판을 통한 IP 주소 추적
웹 게시판에 글을 작성하면 웹서버 또는 App의 로그에 접속자의 IP 주소가 기록 될 수 있다.

* 웹서버 로그: 접속 IP, 요청 시간, 요청 URL 등의 정보를 기록할 수 있다.
* 게시판 기록: 서비스 설정에 따라 게시글 작성자의 IP 주소를 저장할 수 있다.

> 서버 로그는 보통 관리자 권한이 필요하다.

## traceroute를 통한 IP 주소 추적
traceroute는 패킷이 목적지까지 이동하는 과정에서 거치는 라우터(Hop)와 네트워크 경로를 확인하는 도구다.

OS별로 명령어가 다르다.
* Window: `tracert`
* Linux/macOS: `traceroute`

**동작 원리**
1. TTL 을 1부터 순차적으로 증가시키며 패킷을 전송한다.
2. 라우터는 패킷을 전달할 대 TTL을 감소히킨다.
3. TTL이 0이 된 라우터는 일반적으로 ICMP Time Exceeded 메시지를 반환한다.
4. 반환된 메시지를 이용하여 경유한 라우터의 IP 주소와 응답 시간을 확인한다.

** 명령어 예시**
```shell
# Windows
tracert example.com

# Linux / macOS
traceroute example.com
```

> Windows tracert는 기본적으로 ICMP Echo를 사용하며, Linux traceroute는 일반적으로 UDP를 기본으로 사용한다.

> 일부 라우터는 ICMP 응답을 제한하므로 * * *로 표시될 수 있다. 또한 traceroute는 목적지까지의 경로를 분석하는 도구이지, 상대방의 실제 위치나 신원을 직접 확인하는 도구는 아니다.

> 라루팅 경로는 항상 일정하지 않기 때문에 항상 값이 일치하지 않는다.

## IP 주소 추적의 한계

IP 주소를 확보한 뒤 WHOIS/RDAP 및 GeoIP 등의 서비스를 이용하면 추가적인 정보를 분석할 수 있다.

* **WHOIS/RDAP:** IP 주소의 할당 기관, 네트워크 사업자 등의 정보 확인
* **GeoIP:** IP 주소에 연결된 대략적인 국가 및 지역 정보 추정
* **VPN / Proxy:** 실제 사용자의 IP 대신 중계 서버의 IP가 나타날 수 있음
* **NAT / CGNAT:** 여러 사용자가 하나의 공인 IP를 공유할 수 있음

> 핵심은 IP 주소를 확인하는 것과 실제 사용자를 특정하는 것은 다르다는 점이다. IP 주소만으로 정확한 위치나 개인의 신원을 확정할 수 없다.
